# Домашнее задание к занятию «Резервное копирование баз данных»

## Задание 1. Резервное копирование

### 1.1. Восстановление данных в полном объёме за предыдущий день

Для такого требования подходит ежедневное полное резервное копирование.

Например, каждую ночь в 02:00 создаётся полная резервная копия базы данных. При возникновении неисправности база восстанавливается из последней успешно созданной копии.

Пример схемы:

```text
Понедельник 02:00 — полная резервная копия
Вторник 02:00 — полная резервная копия
Среда 02:00 — полная резервная копия
```

Если сбой произошёл в среду днём, данные можно восстановить из копии, созданной в среду в 02:00.

Преимущества:

* простое восстановление;
* для восстановления требуется только один файл или комплект резервной копии;
* легко организовать хранение копий за несколько предыдущих дней.

Недостатки:

* полное копирование может занимать много времени;
* резервные копии занимают много места;
* изменения, сделанные после последней копии, будут потеряны.

Для надёжности резервные копии необходимо хранить отдельно от основного сервера базы данных, например в объектном хранилище или на другом сервере.

### 1.2. Восстановление данных за час до предполагаемой поломки

Для восстановления на определённый момент времени подходит сочетание:

* периодической полной резервной копии;
* инкрементальных копий;
* журналов транзакций.

Например:

```text
Воскресенье 02:00 — полная резервная копия
Каждый день 02:00 — инкрементальная копия
Каждый час — сохранение журналов транзакций
```

При восстановлении сначала разворачивается последняя полная резервная копия, затем последовательно применяются инкрементальные копии и журналы транзакций до нужного времени.

Для PostgreSQL используется архивирование WAL и механизм Point-in-Time Recovery.

Для MySQL могут использоваться binary log и механизм Point-in-Time Recovery.

Этот вариант позволяет восстановить состояние базы примерно за час до сбоя или до другого указанного момента времени.

Преимущества:

* потеря небольшого объёма данных;
* возможность выбрать точку восстановления;
* инкрементальные копии создаются быстрее полных.

Недостатки:

* восстановление сложнее;
* необходимо хранить полную цепочку резервных копий и журналов;
* повреждение одного элемента цепочки может осложнить восстановление.

## Задание 2. PostgreSQL

### 2.1. Создание резервной копии

Для создания резервной копии базы `app_db` в custom-формате используется команда:

```bash
pg_dump \
  -h localhost \
  -p 5432 \
  -U postgres \
  -d app_db \
  -Fc \
  -f app_db.dump
```

Параметры:

```text
-h localhost   — адрес PostgreSQL
-p 5432        — порт PostgreSQL
-U postgres    — пользователь
-d app_db      — база данных
-Fc            — custom-формат архива
-f             — имя выходного файла
```

Проверить создание файла можно командой:

```bash
ls -lh app_db.dump
```

### Создание базы для восстановления

```bash
createdb \
  -h localhost \
  -p 5432 \
  -U postgres \
  app_db_restore
```

### Восстановление базы

```bash
pg_restore \
  -h localhost \
  -p 5432 \
  -U postgres \
  -d app_db_restore \
  app_db.dump
```

Если нужно перезаписать объекты в уже существующей базе:

```bash
pg_restore \
  -h localhost \
  -p 5432 \
  -U postgres \
  --clean \
  --if-exists \
  -d app_db_restore \
  app_db.dump
```

Также можно создать архив, содержащий команду создания базы:

```bash
pg_dump \
  -h localhost \
  -U postgres \
  -d app_db \
  -Fc \
  --create \
  -f app_db.dump
```

Восстановить его можно так:

```bash
pg_restore \
  -h localhost \
  -U postgres \
  --create \
  -d postgres \
  app_db.dump
```

## Задание 3. MySQL

### 3.1. Инкрементальное резервное копирование

В MySQL инкрементальное резервное копирование можно организовать с помощью binary log.

Binary log содержит события, изменяющие данные базы. После создания полной резервной копии сохраняются новые binary log. Они содержат изменения, выполненные после полного копирования.

Проверка состояния binary log:

```sql
SHOW VARIABLES LIKE 'log_bin';
```

Ожидаемое значение:

```text
log_bin | ON
```

Посмотреть список журналов:

```sql
SHOW BINARY LOGS;
```

Перед созданием очередной инкрементальной копии необходимо переключить текущий binary log:

```bash
mysql -u root -p -e "FLUSH LOGS;"
```

После этого текущий журнал закрывается и создаётся новый.

Пример просмотра файлов:

```bash
ls -lh /var/lib/mysql/mysql-bin.*
```

Закрытые binary log, появившиеся после последней полной или инкрементальной копии, необходимо скопировать в каталог резервных копий:

```bash
mkdir -p /backup/mysql/incremental

cp /var/lib/mysql/mysql-bin.000001 \
   /backup/mysql/incremental/
```

На следующем этапе копируется следующий закрытый журнал:

```bash
mysql -u root -p -e "FLUSH LOGS;"

cp /var/lib/mysql/mysql-bin.000002 \
   /backup/mysql/incremental/
```

Таким образом, каждый сохранённый binary log является частью цепочки изменений после полной резервной копии.

### Восстановление

Сначала восстанавливается полная резервная копия:

```bash
mysql -u root -p app_db < full_backup.sql
```

Затем применяются сохранённые binary log:

```bash
mysqlbinlog \
  /backup/mysql/incremental/mysql-bin.000001 \
  /backup/mysql/incremental/mysql-bin.000002 |
mysql -u root -p
```

Можно восстановить данные только до определённого времени:

```bash
mysqlbinlog \
  --stop-datetime="2026-06-14 12:00:00" \
  /backup/mysql/incremental/mysql-bin.000001 |
mysql -u root -p
```

### Альтернативный вариант: MySQL Enterprise Backup

В MySQL Enterprise Backup существует отдельная команда `mysqlbackup` для создания инкрементальных копий.

Пример:

```bash
mysqlbackup \
  --defaults-file=/home/dbadmin/my.cnf \
  --incremental \
  --incremental-base=history:last_backup \
  --backup-dir=/home/dbadmin/temp_dir \
  --backup-image=incremental_image1.bi \
  backup-to-image
```

Этот вариант требует наличия MySQL Enterprise Backup. Для обычной MySQL Community Edition можно использовать binary log.
